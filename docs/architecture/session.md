# Session

The title screen, its controls, How to play and Settings pages, run lifetime, first-play tips, and fixed-step delivery to the survival game.

## Current decisions

- `src/session/` receives a survival run factory and a `CinematicStage` from `src/scene.cpp`. It decides which screen is open and delegates drawing to rendering and HUD.
- The start screen is the title screen, the main menu, listing New game, Controls, How to play, Quit, and Settings, with Continue inserted first when the day slot is readable. W or up and S or down move its cursor, wrapping at both ends, and Enter takes the marked entry; 1 to 4 take the first four entries directly; entries after the fourth have no number key, because `src/input/` binds only 1 to 4. The cursor stays where it was when a screen returns to the title. New game opens the choice of players: the chef, the appraiser, or two local players, taken with the same cursor keys and Enter, or by 1, 2, and 3 directly. Its cursor also stays where it was when the screen opens again. Controls opens a page listing both players' keys. Settings opens a page of the resolution and window rows, each a name, two arrows and a value, which W or up and S or down choose between and A or left and D or right and a click on an arrow change, as on the pause screen. How to play opens a page of the first-play tips' lines, in their order, under one line on what the game asks. M or Esc goes back from the choice of players, the controls page, the How to play page or the Settings page to the title screen. Mid-run in the survival game M asks first, below. The title and these pages are drawn in the UI kit: the title is a picture across the screen with a menu panel holding a dark button for each entry and a gold one under the marked entry, and each page is a kit panel with a kit button as its way back; `src/hud/title.cpp` draws them and records each frame in the `title_frames` meta, which `project/e2e/title.gd` reads and `project/e2e/title_capture.gd` checks in pixels on a 1920x1080 window ([ADR 0037](adr/0037-draw-the-title-and-its-pages-in-the-ui-kit.md)).
- The session receives the single save slot's read and update operations from `src/scene.cpp`. A fresh run stores day one before the intro, and each day-finishing command or base timeout stores the next day immediately after the ending judgment, before another command or time can change it. Every transition within a long frame is saved. Both endings and acid loss remove the slot before their cinematic. Opening New game or its setup does not touch the slot; starting its run overwrites it.
- `src/survival/` owns the typed day checkpoint and versioned serialization. It preserves the date, acid, seed, both inventories, fridge, identified ingredients, stored dishes and quality, feeding history and last result, satisfaction count, workshop random sequence, remaining container stock, touch counters and local roles. Fixed base positions, full daily clocks and the date-dependent world are reconstructed. The format is checked against current content and timing; incompatible versions, oversized or malformed files, unknown identities and invalid day states yield no checkpoint. The slot lives at `user://day.save`; I/O failures never stop play, and write or removal failures reach a host warning.
- Continue opens the saved day directly at base with its saved roles, without the intro. Input must be released as for every transition. Tutorial tips and presentation state begin afresh; time and commands later in the saved day are discarded. The title checks the slot when it opens and again when Continue is chosen, so a file that became unreadable cannot start a run. [ADR 0041](adr/0041-autosave-one-start-of-day-slot.md) records the recovery boundary.
- Session keeps the frame the run reported before a change of map while a map fade darkens the screen, and draws, aims and targets clicks from it until the fade is black, as ADR 0031 decides; the run, its status and its time are the new frame's from the change on.
- Session receives a `SoundStage` from `src/scene.cpp` as it does the `CinematicStage`, in the cues, tracks and buses `src/audio/` names. It decides which cue each menu step, choice and going back, and each frame of play, plays, and which music each screen plays; it keeps the effects and music volumes, from 0 to 10, 8 and 6 at start, for as long as the host runs, and sends them to the stage. Effects at 0 play no cue and music at 0 plays no music, and the stage mutes that bus. On the pause screen W or up and S or down choose a row of the two volumes, the resolution and the window mode, and A or left and D or right change a volume by one or a display row by one place, with the move cue as feedback. `project/e2e/audio.gd` plays with real key events and reads `sound_status()`: the menus' cues, each screen's music, a cinematic's silence, the cues and flourishes of walking, jumping, landing, collecting, travelling, appraising, cooking, feeding and a new day, the music's tension after the acid rose, a fall into the acid, and that with effects at 0 the next day turns and fades with no cue started while with music at 0 nothing plays, each with the volume raised again as control.
- Session receives a `DisplayStage` from `src/scene.cpp` too, holding the choice read from `user://` when the host opens, the size of the display, and the call that applies and stores a new choice. It decides what a change means, as [ADR 0024](adr/0024-render-a-1920x1080-canvas-at-the-output-resolution.md) states: in full screen the resolution row shows the display's size and refuses its arrows with a reason, in a window the sizes stop at the largest that fits the display, and a change that would leave the choice as it was is neither stored nor answered with a cue. A choice the host could not store stays in force and shows in `display_status()`.
- A survival run can be held by one `hud::Interruption` at a time: Esc pauses, showing every key of the current number of players, the volume and display rows, the recipe book with what feeding does, and what ends the run well, and M asks before leaving, warning that progress in the current day is not saved. Enter accepts, and only there. Esc cancels, back to the run, or to the pause screen when M came from there. A second M answers nothing, because M is the key that may be pressed by mistake.
- A held run takes no key and no time: neither `Simulation`'s clock nor `SurvivalRun`'s accumulated frame time moves, and the part of a step already played is kept. The frame of the press was played up to it, so it spends its time, with no key; pending edges are dropped first, so a press from before the hold cannot act minutes later. Continuing waits, with a message on screen, until every control of both key sets is up, the same rule as a transition, so a key held across a hold does not act. A cinematic and a run that just ended are not held: Esc does nothing there, and M keeps the cinematic contract below.
- After a two-player run's hand-off the goal line under the acid names the actor left and its movement keys, since [a lone human holds the first set](survival.md#companion-and-control) and the second set stops answering. A run that opened with one player shows nothing.
- A run's first-play tips are one line on each concept, opened the first time the run shows it and never again in that run, as [ADR 0016](adr/0016-teach-each-concept-once-in-a-tip-that-never-holds-the-run.md) decides; a new run opens them afresh. `src/session/tips.cpp` decides when each is due from the frame's snapshots: setting out while the party is at base with time left; a carried find not yet identified; a recipe ready at base; a stored dish at base; a hated dish; acid above 0; and the ending once a day has finished. Tips open at base only, as [ADR 0034](adr/0034-show-exploration-as-the-mockup-top-bar-and-one-action-prompt.md) decides, so the move and collect tips never open and the controls page alone lists them; one tip shows at a time, the first due in that order. It never holds the run: it closes on any click, on a human's travel, interact, feed or end-day key or a dish choice, after 8 seconds of play, a temporary value, or when the party sets out, and a held run does not age it. `survival_status()` reports the open tip as `tip` and the opened ones as `tips_opened`.
- The base clock and the cook run in the workshop phase on the same fixed 100ms unit as exploration: each step calls `Workshop::advance` once the exploration has advanced, as [ADR 0035](adr/0035-lower-acid-on-feeding-time-the-cooking-and-give-the-base-five-minutes.md) decides. `survival_status()` reports `cooking` (whether a cook runs), `cooking_progress` (float 0 to 1, 0 when none), `cooking_food` (the dish's name, empty when none), `ingredient_slots` (the display names of the ingredients in the slots, empty when none), `ingredient_slot_count` (how many the slots hold at most), `base_timed` (whether the base has a clock) and `base_remaining_ms` (the base time left, 0 with no clock). A dish chosen on the screen is forgotten when the day changes. `day_lengths_from_environment()` reads `NEOCITY_EXPLORATION_SECONDS`, `NEOCITY_BASE_SECONDS` (0 for no clock) and `NEOCITY_COOK_SECONDS` into the `DayLengths` that `MainScene::start_survival` gives `temporary_content`; the Makefile sets them only for the Godot checks, never for `run`.
- Quit quits through the engine's main loop, the one operation session does not receive from `src/scene.cpp`.
- Every transition clears the open game's run and its interruption and closes any cinematic. Controls must be released before the next screen accepts input, so a held key cannot become its first action.
- A click presses the key that the thing under the mouse stands for, as [ADR 0013](adr/0013-click-what-the-screen-shows-as-its-key.md) decides. Each frame, after the run's frame is aimed, session asks `src/hud/` for the clickable things of the open screen as it is drawn, each a `hud::Target` with its area, its press and, while it would do nothing, its reason. A click on the next frame acts on what the player saw: session sets the press on that frame's `Command`, a menu entry's number, Enter, Esc or M, a human's interact, search, feed, end-day or travel key, or a slot of the transfer screen, or the chef's dish step, before the screen advances, so a click takes the same path as its key. A volume block sets its row's level; a row's name is not a target, so a click cannot mute a volume by mistake, and the left key takes a volume to 0. A target that refuses presses nothing. The mouse button is a control, so a click held across a transition waits like a key. With two players the screen names who acts: at base the role decides, cooking, feeding and ending the day the chef's and appraising the appraiser's, and the set-out step sets out every human at base; in the city each human's own action prompt is the only target, pressing the search or the travel key it names.
- For the survival game, `SurvivalRun` accumulates real frame time, unbounded, into fixed 100ms steps, as the [PM decision on #28](https://github.com/garamsh/neocity/issues/28#issuecomment-6553578708) requires, so time is neither lost nor doubled at any frame rate. Godot cuts `delta` to what `physics/common/max_physics_steps_per_frame` allows at the physics tick rate, which at the defaults of 8 steps and 60 ticks a second loses time below 7.5 fps, so `project/project.godot` sets 100000, a frame of about 28 minutes. Nothing steps on physics ticks, so the tick rate keeps Godot's default. The step clock runs in every phase: each step applies both actors' commands and calls `Exploration::advance` once with `Simulation`'s acid, and `Exploration` spends exploration time only while someone explores, so expiry leaves no remainder to carry and workshop steps spend nothing. A new run starts from an empty accumulator.
- `SurvivalRun` owns each human's transfer screen: it opens it when the search key finds a container in reach or at base, keeps its cursor on the container's slots first, moves the cursor with the movement keys once per press (a click on a slot puts it there and presses the interact key), and turns the interact key into the `Take`, `Put`, `Store` or `Withdraw` the cursor stands on, which `Companion` applies like any other action; with no container in reach in the city the interact key on an open screen does nothing, and at base it moves an item, so cooking and appraising wait for the screen to close. The screen closes when the search key is pressed again, when the actor changes place or is sent away, when the container closes under it, and when the actor has no human left; it reads the run's views and moves nothing in the rules. `project/project.godot` binds `survival_1_search` to R and `survival_2_search` to P.
- A survival step reads a fresh view for each actor after applying the other's action. Edges are retained until a step consumes them. When an actor's location changes between the city and base, for any cause, that actor's interact edge is dropped for the next 0.3 seconds of game time, a temporary value, and in the step of the change if it came before that actor's command, so an interact aimed at the old place, made on a screen a step or a reaction behind, does not act in the new one, as [#83](https://github.com/garamsh/neocity/issues/83) records. Travel, feed, end day, movement, pause, and the leave question are not held, and a held run takes no step, so the hold does not run down. A direction press shorter than a step walks one step; a key held across a step stops walking when released. A press and release inside a single frame arrives as `PlayerInput`'s `tap`, walks one step at any frame length, and takes that step from a key still held. A jump press is an edge retained until a step consumes it, so a tap between steps jumps once and a held key jumps only once.
- When two humans finish the day in one step, only the first command runs; `SurvivalRun` compares the day before each day-finishing action.
- `SurvivalRun` ignores the last human's leave, because a party of AI alone has no key to take an actor back. When two humans leave in one step, the chef's leave applies and the appraiser's human stays.
- `SurvivalRun` calls `Endings::check` after each command, so a finished day is judged before the partner's command can set out. An ending or a loss ends the step and the run takes no further step. The rules decide a loss first, as [survival](survival.md#loss) records.
- `SurvivalRun` holds a human chef's chosen dish, since `Companion`'s offer is only a suggestion. A press of up or down in the workshop phase, read from the key itself and not from movement's held direction, moves the choice through the dishes that can be cooked now, wrapping at the ends; a held key is one press, and other held keys do not change that. With a choice that can be cooked, the chef's cooking is that `Cook`, for the key and for the screen's offer alike, so the dish named is the dish cooked. With no choice, or one whose ingredients ran out, the chef's key cooks `Companion`'s offer, and the panel marks that instead. A choice lasts for the day, so yesterday's dish does not override an uneaten one. An AI chef is not affected. Using the movement keys adds no input action; these bindings are temporary.
- `SurvivalRun` records actions, falls, expiry, destruction, and exposure as events for the screen. A bag appearing or destroyed shows on the map and is not an event, because the tide brings bags every day and a four-line log would lose everything else to them. It counts the city's other changes per finished day, the changes the day's stage caused. Each event takes the next number of the session's log, a new run continuing the last, so the screen tells one note from another by it.
- The game status carries `world_day`, `damage_stage` and `map`, `mutants` (each current-map mutant's `sub_x` and `sub_y`) and, for each actor, `absent_ms`, the time left of a touch's absence or -1 on the map, as [ADR 0030](adr/0030-patrol-mutants-and-fixed-obstacles-send-an-actor-away.md) decides, and `project/e2e/survival.gd` reads them to check that a mutant's position changes and that a touched actor leaves the map and returns, and the current map's objects reach the screen as the view's world, while `objects` and `places` in the status list every map's objects. A run is on the street at the start of each day; the map changes only when both actors stand in an exit zone, as [ADR 0027](adr/0027-fix-the-street-and-aquarium-maps-and-damage-them-by-day.md) decides.
- `project/e2e/survival.gd` checks that the base and the first city screen name no key but the prompts' search and travel keys, that the city's HUD is the three plates and one prompt for each human with an action and nothing else, and that on day one at base and with the chef at a source the area of the HUD's panels, from the `hud_panels` meta, is smaller than it was at the same seeded state while every key was named. `project/e2e/survival.gd` clicks with real mouse events where the keys have set the game up: at base the dish line, the feed line, the chef in the kitchen to cook, the dish line while it refuses, which chooses nothing while S chooses, and the end of the day; the appraiser's ingredients; in the city the set-out step, the way to base as the prompt with nothing in reach and the close prompt over the inventory, the prompt to collect, a volume block, a volume row's name, which changes nothing, leave, cancel and continue; and with two players the set-out step for both and the task card's step to cook. `project/e2e/title.gd` clicks the title entries, the controls page's and the How to play page's way back and the choice of players, checks that the title screen and the choice of players name no key, and clicks the bottom of the leave question's button where it is drawn while it still rises into place.
- `project/e2e/survival.gd` plays the game with real key events, pressing for each action the NEXT line names the key the controls page lists for it: two full days as the chef with AI, a third and fourth day ended unfed, a run handing the chef to AI that is told to wait for the AI chef's cooking only while no dish can be fed, a run choosing a dish and following the NEXT order, a run following only the NEXT line to the ending that never ends a day unfed beside a stored dish it would feed, a run as the appraiser, the second key set, two players feeding a dish the monster hated and then finding F does nothing with the one left while the line cooks, then with nothing left to cook sets out while the day has time and ends the day unfed once it has none, two players at base told to set out, no key line in exploration, each human's prompt naming the source it acts on, the way to base with none in reach, whose click travels, and reading close while a search is open, feeding on the task card while the line sets out, a held chef who cannot return to base, the NEXT line naming the time the hold has left, a bag emptied or carried off leaving the map while the rest stay, a run to the ending with a dish ready, the pause screen with what ends the run and what feeding does, drawn there and not under it, the question before leaving, each hand-off, a line that dropped out of the log logged afresh with no note drawn, and quitting, whose pass line prints only once the game has ended the process. Throughout, it reads the tip each frame drew from the `hud_tip` meta and checks that every concept's tip opened, none twice in one run, a later run opened one again, the tips name no key, and while the run was not held no drawn tip covered a HUD panel or a click target or left the screen, with frames drawn as control; at the first base it clicks the set-out tip, which closes it and presses nothing. `project/tests/survival_timing.gd` injects action values to verify the fixed step at 480 and 5 frames per second, retained edges, expiry, the hold on interact after a time-out return with the press after it as control, travel just after arriving and two players setting out in one step, a collection holding the chef in place while the shared clock runs on, the one-day guard, the last-human guard, and that a hold spends and loses no time. `--fixed-fps` bypasses Godot's cut of `delta`, so its `-- real-clock` run delays real frames with no such flag and compares exploration time with the wall clock, frames of up to 2.5 seconds included. `project/e2e/escape.gd` plays from the main menu to the ending with real key events on what the NEXT line says, once at 60 and once at 5 frames per second so that one frame spans two steps, and drives the cinematic contract below with no asset, a working stand-in scene, and broken ones, the placeholder card's Skip and Main menu clicked on the intro and offered on the ending; it installs each stand-in with `Resource.take_over_path`, so nothing is written to the art folders, and its `-- real-clock` run holds the intro card's length on delayed real frames. `project/e2e/loss.gd` does the same to a loss by pressing only the end-day key, and clicks the loss card's Skip. These harnesses walk the way the NEXT line's words say, as a player does. `project/e2e/title.gd` drives the title screen with real key events: each entry by cursor and by number, the cursor's wrap at both ends, the controls page, the How to play page with a line on each concept in order and no key named, and the choice of players and back by Esc and M, each choice of players by its cursor, with its wrap and its kept place, the controls page's rows against the pause screen's for two players, a new game as the chef, and Quit.
- `project/e2e/escape_device.gd` walks both humans from the first base to the device on the aquarium's service roof on real key events with `NEOCITY_ESCAPE_DAY` at 1, searches the cold store's upper shelf, the aquarium's service shelf and its roof crate for the three parts, presses the interact key at the device with two parts, which must change nothing, and with three, which must end the run as `escaped`. It runs headless as part of `make test-escape`.

### Cinematic contract

The agreement between the host and the opening and ending art of [#29](https://github.com/garamsh/neocity/issues/29). The seam is `CinematicStage`, which `src/scene.cpp` provides to session.

- **Location:** `project/levels/monster_mouth_escape/cinematics/intro/intro.tscn`, `project/levels/monster_mouth_escape/cinematics/ending/ending.tscn`, and `project/levels/monster_mouth_escape/cinematics/loss/loss.tscn`, each scene with its assets in its own folder. None exists yet.
- **Scene:** the root is a `CanvasItem`, such as a `Node2D` or a `Control`, because the host paints an opaque dark stage that would hide a 3D root. It declares a `finished` signal with no arguments and emits it once when playback is done; with arguments the host cannot receive it and stays on the scene. The host adds the root as a child of the game scene.
- **Request:** session plays the intro when a run starts, the ending when the run reaches one, and the loss when it is lost.
- **End:** on `finished` the host closes the scene, by the end of that frame. The signal may fire from `_enter_tree` on, `_ready` included; the host connects it only after instantiating, so one fired in `_init` is not heard.
- **Skip:** the interact key of any human closes the scene at once, so a scene cannot rely on reaching its own end. The intro's card draws a Skip and a Main menu button, whose clicks press every human's interact key and M; the ending and loss cards draw a Main menu button alone, and the interact key still closes them.
- **Input block:** while a cinematic is open the run takes no key and no time, and the skip does not reach it. M still leaves for the main menu and ends the run.
- **Return:** the intro hands over to day one at base. The ending and the loss close the run and return to the main menu.
- **Fallback:** a scene that is missing, that does not load as a scene, that does not instantiate, whose root is not a `CanvasItem`, or that has no `finished` signal opens a placeholder card instead, under the same skip, input block, and return. The host never aborts for a cinematic. A skip-free card stands 4 seconds for the intro and 6 for the ending and the loss; the lengths are temporary.

## Rationale

[ADR 0006](adr/0006-ship-one-game-behind-a-title-screen.md) leaves the application one game behind a title screen. Session orchestration leaves the `MainScene` composition contract thin. [ADR 0016](adr/0016-teach-each-concept-once-in-a-tip-that-never-holds-the-run.md) teaches each concept once in a tip that never holds the run, rather than in cards that wait for a key. [ADR 0037](adr/0037-draw-the-title-and-its-pages-in-the-ui-kit.md) draws the title and its pages in the UI kit.
