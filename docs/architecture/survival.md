# Survival Rules

The pure C++ progression state of the monster-mouth escape game and the ownership boundaries of its later features.

## Current decisions

- The `survival` static library in `src/survival/` depends only on the C++ standard library. It does not link with the existing `gameplay`, the experiments, or Godot. Its public boundary is [`include/survival/simulation.hpp`](../../src/survival/include/survival/simulation.hpp), [`include/survival/world.hpp`](../../src/survival/include/survival/world.hpp), [`include/survival/exploration.hpp`](../../src/survival/include/survival/exploration.hpp), [`include/survival/workshop.hpp`](../../src/survival/include/survival/workshop.hpp), [`include/survival/escape.hpp`](../../src/survival/include/survival/escape.hpp), [`include/survival/companion.hpp`](../../src/survival/include/survival/companion.hpp), and [`include/survival/content.hpp`](../../src/survival/include/survival/content.hpp), and internal implementation and unit tests sit in the same library's `src/`.
- [`Simulation`](../../src/survival/include/survival/simulation.hpp) owns the two actors' location, exploration health, inventory, carried tools, and exhaustion count, plus the day count, phase, shared remaining exploration time, acid, and run seed. It offers value snapshots and explicit commands for entering, returning, damage, collecting ingredients and tools, advancing time, consuming ingredients and tools, finishing the day, and escaping. The base is part of the untimed workshop phase.
- Exploration time passes only while at least one actor is exploring. On expiry both return to base and the phase changes to the workshop phase. When one actor runs out of health, only that actor returns, preserving the day count, inventories, shared remaining time, and acid. Voluntary return, health exhaustion, and time expiry all restore the returning actor's health to 3 slots. Switching to the workshop phase and stopping time when both are at base is a temporary boundary of the current foundation and does not settle the final base time rule.
- With time remaining, an actor can re-enter with recovered health. The 3-slot recovery on returning to base follows the [user decision record](https://github.com/garamsh/neocity/issues/23#issuecomment-6544525723).
- The caller supplies a positive exploration budget and a seed. Progress is independent of frame partitioning when the same command order and total exploration time are passed directly to the shared `Simulation`. Time is passed as integer microseconds rather than wall-clock time, and negative time is refused with no state change. This guarantee does not extend to exploration return times that follow from world changes.
- The seed is a run-identifying input preserved in the snapshot, and `Workshop` reads it to initialize its own random state. `Simulation` consumes no random values. The Godot host connection and the screen are in [session](session.md) and [presentation](presentation.md).
- Tests are in [`src/simulation_test.cpp`](../../src/survival/src/simulation_test.cpp), [`src/world_test.cpp`](../../src/survival/src/world_test.cpp), [`src/exploration_test.cpp`](../../src/survival/src/exploration_test.cpp), [`src/workshop_test.cpp`](../../src/survival/src/workshop_test.cpp), [`src/escape_test.cpp`](../../src/survival/src/escape_test.cpp), [`src/companion_test.cpp`](../../src/survival/src/companion_test.cpp), and [`src/content_test.cpp`](../../src/survival/src/content_test.cpp), registered in the same `survival_test`. Checks that directly compose world, progression, exploration, and workshop together are library integration tests and do not verify the real screen connection. `project/e2e/survival.gd`, `project/e2e/escape.gd`, `project/e2e/loss.gd`, and `project/tests/survival_timing.gd` verify that connection.

### World state

- `World` distinguishes NPCs, terrain, buildings, ladders, entrances, and material sources by identifier. The caller supplies each object's integer world area, damage and exposure thresholds, material source owner and supplied item, and passage repair tool. A material source supplies exactly one ingredient or tool. It embeds no final map or tuning values. IDs persist through destruction and exposure, and value snapshots give state, traversability, and supply availability. The traversable value applies to terrain and passages and does not imply collision checks of any other kind.
- A material source can supply when it is itself intact and, if an owner is configured, that NPC, building, or terrain is also intact. An owner not yet visible does not supply. Exploration validates acquisition and stock use for ingredients and tools alike. Repair is allowed only on destroyed ladders and entrances that require a configured tool.
- Progression input is the whole run's cumulative exploration time and the current acid. A regression in cumulative time refuses the entire input, and an identical input does not transition state again. An acid drop changes only the current value and does not roll back the historical peak acid or the destruction and exposure history. The return-to-base and health-recovery commands neither own nor reset the world.
- Damage occurs when either a configured time threshold or a peak-acid increase threshold is met. It measures from the run start at first, and the same cumulative measure applies while unexposed. Repairing a passage moves only that object's reference point to the current cumulative time and peak acid. The same hazard input does not undo a repair, and the passage breaks again when added time or a new peak-acid increase reaches the threshold again. This is the current minimal damage model and not the final corrosion and repair balance.
- Exposure persists once a configured cumulative time or peak-acid threshold is crossed. Caller configuration verifies cases where a building is destroyed and other buildings, passages, and material sources appear. Debris physics, chained collapse between buildings, and a real new screen are not implemented.
- `Exploration` adds the shared exploration time it actually consumed to the existing world cumulative time exactly once. The caller does not separately call `Simulation`'s time advance or `World`'s cumulative time update in the same frame. Returning does not reset the cumulative time or the world instance. The exploration caller supplies current acid separately. `Simulation`'s acid is the real value, and `Exploration.advance` does not read it directly. The host composes these concrete features at the existing single composition site and passes input, time, and `Simulation`'s acid.

### Exploration behavior

- `Exploration` does not own the `Simulation` and `World` it receives. It owns both actors' detailed positions and stamina and the shared material source stock, and applies entry, return, damage, and collection through the existing progression commands. Actor position and time commands during a run go through exploration.
- The four-direction integer grid is a temporary movement representation. Actors move across cells supported by intact terrain, ladders, and entrances, and intact buildings and broken passages block. An intact entrance or ladder overlapping a building opens that cell and a broken passage blocks first, so world object order does not change the result. An actor returns when support disappears or on entering an unsupported cell. Running also checks passage cell by cell. Final physics and camera are not decided.
- Movement is in 100ms units, and the leftover movement time of short frames is preserved per actor. Actual exploration time is consumed immediately on every call. Both actors' inputs are taken together, the shared time is consumed once, and movement after expiry is forbidden. World changes apply at the end of the supplied time interval, and continuous physics checks at the moment of damage are not implemented. `Exploration`'s return time on observing destruction and the actual time consumed can therefore vary with how calls are partitioned. The Godot host delivers one constant 100ms unit, so its results do not.
- Each collection, ingredient or tool, spends `ExplorationConfig::collection_time` of the shared clock, the same for a human and AI, and advances the world by that time once. A collection the clock cannot cover spends what is left, keeps its item, and returns both actors as expiry does. A refused collection spends nothing, and a return gives no time back.
- Walking and running move one and two cells per movement unit, and running uses one stamina slot. With no stamina the actor walks, and each non-running unit recovers one slot. Maximum stamina, interaction distance, start point, and stock are caller inputs and all temporary tuning values. The two roles have no difference in ability.
- Vending machine, NPC, shop, and bag markers all connect to the world's material source IDs. The ingredient collection command applies after checking that the material source exists and its access distance, supply state, and remaining shared stock. Spent stock is not restored by returning or setting out again, and tools are not represented as ingredients. Returning and health recovery neither remove nor duplicate carried tools.
- Tools found in the city use the same collection command and checks as ingredients and enter the collecting actor's `tools`, never its ingredient inventory. `ToolId` is the carried tool's type, and the caller's configuration decides what each ID does: the passage's repair tool, or the workshop's magnifier and spatula replacements.
- `Exploration` is the repair command for play. It checks that the actor is in the city, within interaction distance of the object, and carrying the named tool, and `World` then checks the tool against the passage. `World` alone does not know who carries what.
- A manual return, a fall, health exhaustion, or expiry sets the detailed position to base. Setting out again starts at the designated city entrance and does not reuse earlier partial movement. Collection requests are not retained, so an earlier request does not run on the next departure. Inventories, the world, and shared time are preserved under the existing progression rules.

### Workshop work

- `Workshop` does not own the `Simulation` it receives. It owns role checks, identified ingredients, tool state, stored food, the history of fed foods and ingredients, the last day's result, and its own random state. `Simulation` handles atomic ingredient consumption, acid, the next-day transition, and exploration budget restoration. This boundary follows the [PM decision](https://github.com/garamsh/neocity/issues/26#issuecomment-6553559757).
- All workshop commands apply only in the workshop phase with both actors at base. The exception is tool damage, which applies until the run is over so that events during exploration can also be delivered. Workshop commands use no health, stamina, or exploration time and have no time limit.
- Only the appraiser appraises and only the chef cooks. Feeding and ending the day unfed are not tied to a role. An appraisal result distinguishes only success or failure and the identified ingredient, and whether failure is misinformation or a failure indication is not decided.
- The tools' intact 90% and damaged 40% are a [user decision](https://github.com/garamsh/neocity/issues/21#issuecomment-6526232827). The state of the two base tools is workshop state, separate from the carried `ToolId` items that replace them. Replacement needs the configured tool carried by either actor, and is refused on an intact base tool so that no tool is spent for nothing. Connecting other damage events belongs to the caller.
- Exhaustion reaches the base tools without `Exploration` depending on `Workshop`: `Simulation` counts each actor's exhaustions, and `Workshop` derives a tool's state from that count against the count at its last replacement. Every path to exhaustion therefore counts, and a snapshot cannot lag behind it.
- `Simulation`'s finish-day raises acid, moves to the next day, and returns the exploration budget to its configured value. Acid stops at full. Feeding or ending the day unfed finishes the day in one command, so there is one feeding per day. The world and stock are not reset by the day.
- The last day's result is the finished day, the monster's reaction, the score, the acid rise, and on a fed day the dish with its score part by part. `dish_score` computes those parts from a dish and the eating history, for feeding and for the screen's forecast alike, and reads no `Recipe::disliked`.

#### Randomness

- The owner is `Workshop`. Appraisal and cooking share one `std::mt19937` initialized once at construction from the run seed.
- Consumption order is command call order. One actually attempted appraisal or cooking consumes one value, and the snapshot's `rolls` shows the cumulative consumption count. Cooking rolls after consuming ingredients. Invalid role, phase, and ingredient requests consume neither state nor random values.
- The roll is the engine output modulo 100, and it succeeds below the tool's success percentage. A cook's same roll also decides the dish: the lower half of the success range is fine and the upper half plain, so no extra value is consumed and a damaged spatula cooks fewer fine dishes. Only the engine output fixed by the standard is used, and standard distributions, whose results differ by implementation, are not. The bias from `2^32` not being a multiple of 100 is at most 96 in `2^32`.
- There is no general random service. `Escape` owns a second stream, described in [Escape](#escape). Consumption in one stream never moves the other.

#### Temporary policies

The following are temporary values that make the prototype playable and are not final balance confirmed by the user.

- Recipes, disliked food markers, new food and new ingredient scores, the satisfaction threshold, and acid rises are supplied by the caller and have no default. Flavors and the fine dish score default to adding nothing.
- The score adds the first-eaten food score, the score for each first-eaten ingredient kind, each ingredient's taste, and the fine dish score for a fine dish. Novelty and taste are added, so that the threshold can demand both: the [user decision](https://github.com/garamsh/neocity/issues/21#issuecomment-6566139712) is that new and delicious food holds the acid, and that taste depends on the ingredients and the cooking result.
- At or above the threshold acid does not rise. Below it acid rises by the configured amount scaled to the shortfall, rounded up, so a bland repeat costs more than a delicious one and any meal below the threshold raises acid. A disliked food raises acid by its configured amount regardless of score, and `WorkshopSnapshot::rejected_foods` remembers it. No feeding lowers acid.
- Ending the day without feeding is a [temporary PM decision](https://github.com/garamsh/neocity/issues/26#issuecomment-6553559757) that keeps the date from being blocked by a lack of ingredients. The acid penalty is a call input, and the command creates no ingredients or food.
- Cooking needs every ingredient of the recipe to be identified. Identification is per ingredient kind and lasts the whole run. Retries after a failed appraisal are not limited. Re-appraising an already identified ingredient is refused.
- A failed cook consumes the ingredients and makes no food. Food is stored until fed and does not spoil with the date.
- Replacing a magnifier or spatula spends one carried tool. Repair spends no tool and has no cost; this is one fixed behavior, not a setting.
- One exhaustion damages one base tool: the appraiser's the magnifier, the chef's the spatula. Other health loss, falls, and voluntary and timed returns damage nothing.
- A repair uses a tool carried by the repairing actor, within the same interaction distance as collection.
- At base the two actors' inventories and tools are used together, and the chef's are consumed first. In the workshop phase the day can end even with exploration time remaining, and the remaining time does not carry over.

### Escape

- `Escape` does not own the `Simulation` it receives. It owns the daily check and its own `std::mt19937`, seeded once at construction from the run seed and a fixed stream constant through `std::seed_seq`, whose output the standard fixes. Building an engine from the run seed alone would repeat the workshop rolls, so that form is not used.
- A check applies in the workshop phase, rolls once for the latest finished day, and consumes one value. A repeat call on the same day draws nothing, so the host checks after every command. A roll waits while the party is in the city.
- A hit calls `Simulation::escape`, which applies only in the workshop phase.

#### Temporary escape values

These make the ending reachable and are not final balance confirmed by the user.

- The first check follows the finishing of day 30, so day 30 counts. Each later finished day is checked.
- A check hits at 20%, a flat chance that does not grow. The values are `TEMPORARY_ESCAPE` in `escape.hpp`.
- A hit is taken at once: the player does not accept the chance, and the party escapes wherever the day ended. What causes the escape is not depicted.

### Loss

- Acid reaching `Config::full_acid` loses the run, a [user decision](https://github.com/garamsh/neocity/issues/21#issuecomment-6566136667). The value is a rule, and the screen reads it. `Simulation`'s finish-day sets `Phase::Lost` inside the same command that raises acid, on the day counter's new day, so nothing can act between the two. Health exhaustion is not a loss, and a loss takes no inventory.
- **Escape and loss on one day:** the loss comes first. Finishing the day decides the loss, and `Escape::check` then finds the run over, reports `NotDue`, and draws nothing, so a day that fills the acid cannot escape on that day's check.
- After either end of the run no command of `Simulation`, `Exploration`, `Workshop`, or `Escape` changes any state: `enter` and `Exploration::advance` answer `RunOver`, tool damage is ignored, and the other commands keep their existing refusals. `SurvivalRun` runs no further step. `World` has no phase: a caller holding it directly can still call `update` and `repair`, and play reaches them only through `Exploration`.

### Companion and control

- `Companion` holds no game state and no random state. It reads `GameView`, a value copy of the four snapshots, and the `ControlMap`, and returns the same `ActorCommand` for the same input. A human's presses and AI's decisions leave as one command type: movement goes to `Exploration::advance`, and an action goes through `apply` to the owning feature, which keeps every refusal and rule. `Companion` updates nothing itself.
- AI reads only what a player has: the snapshots and the recipes and tool identities of the caller's configuration. It does not read `Recipe::disliked`, since a dislike is learned by feeding, and it never observes `Workshop`'s random state.
- `ControlMap` holds one `Controller` per actor. One-player play makes the chosen actor human and the other AI; two-player play makes both human.
- Switching and leaving are separate local commands. Switching trades the two controllers, so a lone human takes the other actor and two humans stay as they are. Leaving hands only that actor to AI. Both keep the actor's position, health, inventory, and tools, because AI continues from the snapshots. The caller owns the `ControlMap`, and the host keeps one human in it, as [session](session.md) records.
- [`src/input/survival.cpp`](../../src/input/survival.cpp) samples Godot actions into `PlayerInput`, bound in `project.godot`.
- Two local key sets exist because two humans share one computer; the two input sets also let a local check drive both actors. A lone human holds the first set on either actor, so switching needs no rebinding. Two humans hold the first set on the chef and the second on the appraiser. The action names and every binding are temporary.
- The caller reads a fresh view for each actor after applying the other's action, and advances at most one 100ms movement tick between commands, because a walking command is valid for one cell.
- `Exploration` and route planning share the public cell rule and area distance in `exploration.hpp`, so a route cannot disagree with movement about a cell. Each command searches reachable cells, at a cost of cells times world objects, which suits the current temporary maps.

#### Temporary AI policies

The following are the minimum that keeps a game from blocking, not final behavior or tactics.

- AI walks and never runs, and collects from every available source with stock, ingredients and tools alike: what the party carries none of first, then the nearest. `Companion::errand` names that target and the first step towards it, so a screen can tell a human the same way.
- AI repairs a destroyed passage with a tool it carries only when nothing is collectable from where it stands and repairing that passage alone brings stock into reach, so a passage with nothing behind it is no errand. A human's key can still repair it.
- AI with a human partner follows that partner: it sets out only while the partner is in the city and returns when the partner is at base, because workshop commands need both actors at base. With an AI partner, each sets out while time remains and something is reachable from the entrance.
- AI in the city with nothing reachable returns to base, and it enters only when something is reachable from the entrance. Expiry returns it otherwise. Waiting at base therefore never holds the day open.
- The appraiser appraises every unidentified carried ingredient and retries a failed roll under the existing unlimited retry policy. The chef cooks one dish when none is stored: an uneaten recipe before a repeat, the tastiest first within each, and never a rejected food. It reads a dislike only from `rejected_foods`, so it can feed a disliked recipe once. Each replaces its own role's damaged base tool when either actor carries the replacement.
- A human in the party owns setting out and ending the day, since AI acting first in an untimed workshop would take the day from them. In an AI-only party the chef ends the day after base work and exploration are done: it feeds an uneaten dish first, then any stored dish, and otherwise ends the day unfed at the caller's `unfed_penalty`. Ending the day belongs to one actor so that one step cannot end two days.
- A human's `interact` picks the first eligible target by the same selection, and the screen names that target. A screen choosing another target builds the `Action` directly, as the host does for a human chef's dish, recorded in [session](session.md). `Companion` lets two humans end the day in one step; the host guards it, as [session](session.md) records.

### Temporary content

- [`content.hpp`](../../src/survival/include/survival/content.hpp) builds one run's map, ingredients, recipes, tools, stock, hazard cells, and tuning for a seed, with display names. Every value is temporary and is not final balance or a final map. Library integration tests in `content_test.cpp` run an AI-only party to day 30 on five seeds, check on those seeds that no day before the first escape check ends unfed, that collection goes on after day 14, and that every stocked source, broken passage, and recipe can be reached and cooked on the map.
- The budget is 45 seconds a day, stamina 20 slots, a collection time of 12 seconds, full acid 100, new food 50, new ingredient 5, satisfying score 100, fine dish 30, disliked rise 15, unsatisfied rise 10 at a score of zero, and unfed penalty 12. Taste per ingredient runs from Pickles 10 to Truffle 55. Every wanted new dish can reach the threshold when cooked fine. A repeat scores its taste alone: only a fine Truffle Roast, Truffle Soup, or Surf and Turf reaches it, and every other repeat falls short.
- The 36 by 16 grid has every source kind, NPC, building, ladder, and entrance kind. The ladder and the door break with time or acid and take the found wrench, and each is the only way to what lies behind it: the rooftop and the cold locker; the vendor, a shop, a kiosk, and a bridge are destroyed; and a ferry drifts in with acid or time and reopens the east when the bridge falls.
- There are 11 recipes, one disliked, so after ten days the acid holds only on a fine repeat of the tastiest recipes, and the other days spend the gauge by how far they fall short. That is what makes taste and supply matter to the end of the run.
- The collection time keeps a party from emptying the map on day one, so a day ends by time while stock remains and that stock stays out for acid to take. Eight washed-up bags of 14 arrive as the run's cumulative exploration time passes each bag's threshold, from 120 to 1160 seconds, with the Meat and Truffle bags last.
- Rising acid only takes supply away, the [user rule](https://github.com/garamsh/neocity/issues/21#issuecomment-6526232827): at any exploration time, no ingredient kind has more collectable stock at a higher acid. Acid brings terrain, not stock: the ferry can drift in with acid, and its bag lands by time alone. Each bag has an acid limit, from 40 to 85, which carries it off or sinks it before it lands.
- Acid also destroys the tomato and pickle machines and the lost basket. Stock left in a destroyed source stays in its count and cannot be collected: at acid 60 at least half of the opening ingredient stock is out of reach if no one took it.
- A bag follows exploration time, and time passes only while someone is in the city, so once a party has nothing in reach no later bag lands unless a human sets out and waits. With no acid, stock lands faster than the clock can collect it, so a party runs out of reach only after acid has taken stock, and it then runs on what it carries.
- Thirty dishes for the first escape check take 34 attempts with an intact spatula's 90%, because a burned dish spends its ingredients, and the reachable stock covers that. The collection time, the bag size, the world's time and acid thresholds, and every score above are temporary values for the user's final decision.
- Hazard cells are acid drips: ending a step inside one after starting it outside costs one health slot, so a run that lands past it costs none. Nothing else in play costs health, so this is how exhaustion and tool damage reach a player. `Content` lists the cells, `Simulation`, `World`, and `Exploration` do not read them, and the host calls `Exploration::damage`.

- Features are added as concrete features inside the same `survival` boundary, with no general event bus, shared engine, or empty feature folder. Not all features accumulate in `simulation.cpp`.
- Exploration uses the world's read-only contract. The PM assigns any contract change needed between them to one owner, and neither includes the other feature's internal state.
- Exploration time is delivered to shared progression exactly once. The exploration elapsed amount other features read is the difference in remaining time before and after progression, so it excludes workshop time and overrun after expiry.
- Feature Workers do not modify shared headers, build files, or architecture documents at the same time. Later feature-specific result types and new shared commands are settled in the actual feature issue, and contract changes are gathered to the integration owner before consumers connect.

## Rationale

- The [game baseline](../design/monster-mouth-escape.md) separates user decisions from temporary runtime behavior and open questions. The [parent #21](https://github.com/garamsh/neocity/issues/21) and [foundation #23](https://github.com/garamsh/neocity/issues/23) set the implementation scope.
- This applies the shallow purpose folders and independent rules boundary of the existing [structure](structure.md). It does not change the purpose-based layout of [ADR 0004](adr/0004-adopt-the-godot-cpp-template-layout.md) or the independent rules boundary of [ADR 0005](adr/0005-isolate-experiment-rules-behind-one-host.md), so no new ADR is added.
- The distinct exploration and base behaviors and the two actors' return-preservation rules are the responsibility of an independent survival library. Adding no branch to the existing ascent game or experiments lets each set of rules be verified separately.

## Open questions

- The distinction between both actors briefly returning and actual cooking, and the final behavior of the exploration clock during a base stay. Currently both at base is treated as the untimed workshop phase.
- The real exploration budget, acid units, the final rise formula, world damage and arrival thresholds, final repair cost and tool consumption, next-day start conditions, final movement physics, and later feature-specific result types. Test inputs do not imply balance decisions.
- Whether appraisal failure is misinformation or a failure indication, retry limits, tool damage conditions, the final result of cooking failure, and the unfed acid penalty and feedings per day.
- The final timing and probability of the daily escape chance, whether it grows, how a player accepts it, and what causes the escape.
- Whether AI should end the day or set out on its own when its human partner stays idle. Currently AI waits for the human.
- Whether a human appraiser can direct an AI chef's dish. Currently the AI chef picks its own.
- The save and restore format. Current snapshots are read-only value passing and not a save file or restore.
